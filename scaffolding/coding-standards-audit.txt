CODING STANDARDS AUDIT - gibbus
Read-only review, 2026-10-04

Interpretation
--------------
CODING_STANDARDS.md was treated as legacy guidance, not an authoritative
specification. Findings below distinguish clear conflicts from policy candidates.
No library, test, build, or repository documentation files were changed.
Locations are relative to the repository and refer to the reviewed working tree.
This is a static conventions audit, not a proof of numerical correctness.

An AST inventory covered all 57 library Python files. Its raw results are in
coding-standards-inventory.jsonl alongside this report. It found:
  145 non-nested definitions with signature defaults (INCLUDING public APIs);
    4 nested definitions with signature defaults;
   17 definitions accepting **kwargs (including intentional compatibility APIs);
   25 imports inside functions;
   36 parameter-documentation candidates;
   26 undocumented non-nested functions/methods;
    5 undocumented classes.
These are candidate counts, NOT counts of confirmed violations. Properties,
publicly accessible component/view methods, storage conversion, compiled ABI
adaptation, mathematical checks, and local kernel constants need context.
There were no bare except/except Exception handlers and no NUMERIC_FAILURES
handlers missing _reraise_if_debug in the Python inventory. Some handlers
nevertheless broaden NUMERIC_FAILURES with ValueError; see below.

1. FAILURE-HANDLING CONFLICTS
----------------------------
High-confidence conflicts with useful current standards:

gibbus\_api\selection.py:326,386,463
  Screening initialization, degree screening, and refinement catch
  (*NUMERIC_FAILURES, ValueError), record the exception as routine, and continue.
  Generic ValueError from NumPy, fitting, or the callback can therefore become a
  rejected candidate instead of a visible contract defect. Debug mode does not
  raise routine failures unless strict mode is also enabled.

gibbus\_api\selection.py:292,298,311
  The score closure itself raises generic ValueError for invalid likelihood or
  dimension, a degenerate component, and unidentified interval components.
  Numerical degeneration/expected candidate rejection should be distinguished
  from invalid contracts with RuntimeError or a typed control-flow sentinel.
  These cases help explain, but do not justify, swallowing all ValueError above.

gibbus\_api\fitting.py:1125-1134
  _run_mixture_fit classifies a generic ValueError by matching
  "point-mixture component is not estimable" in str(exc), then translates it to
  _PointMixtureEstimabilityError. This is precisely the message-based exception
  classification the standards discourage. It is translation, not suppression;
  no missing-ledger allegation is made here.

Policy/contract concern:
gibbus\_api\component.py:111-115
  _natural_params_from_seed catches every ValueError from layout.pack and returns
  None. An incompatible warm-start embedding is a valid reason to decline a seed,
  but this catch also conflates malformed layout/parameter contracts with that
  expected outcome. A typed incompatibility result would make the distinction
  explicit; this is not automatically a swallowed numerical failure.

gibbus\_postfit\resample.py:161-165
  _collect_replicates counts both a wrong-size callback result and non-finite
  values as a failed replicate. Wrong-size output is a callback contract defect,
  not numerical degradation. Non-finite output is discarded without a failure
  ledger event; the aggregate failure count remains visible. This is narrower
  than a claim of completely silent resampling failures.

11. OVERALL PRIORITY AND LIMITS
------------------------------
Most worth reinforcing:
  - Resolve raw samples, supports, degree policies and ORIGINAL observation
    weights once, with robust boundary normalization.
  - Pass explicit canonical contracts and solver/EM policy objects through the
    internal pipeline; do not use generic kwargs to reconstruct defaults.
  - Distinguish malformed contracts from typed numerical candidate rejection;
    keep fallback reporting complete.
  - Protect every C allocation on exception paths, not just allocation failure.
  - Document real numerical guarantees and reusable interface contracts.
  - Consolidate duplicate implementations or record deliberate narrow exceptions.

Keep rather than mechanically remove:
  - Normalization of DERIVED responsibility/component weights.
  - Numerical feasibility, endpoint, coordinate-scale and identifiability checks.
  - Ownership copies/freezing, cache-protection copies and contiguous kernel packing.
  - Compiled allocation fallbacks and exact-rational representability logic.
  - Publicly reachable component/view/compatibility defaults.
  - Truly local numerical constants, justified warm starts and documented cycles.

This report compiles the discovered cases, not an assertion that a static review
found every possible violation or that every candidate should be changed.
